# installer-v0.5.0 estate rollout

This record covers the curator-approved rollout that followed the
[`installer-v0.5.0` Release](2026-10-11-opencode-installer-v0.5.0.md) and a same-day follow-up that
the curator decided after it. The real-profile updates, Codex installs, and deletions are authorized
changes, not isolated panels. `isolation_ok: false` because the follow-up's discovery checks on the
Windows workstation and the Linux host ran against the real OpenCode databases (see
[proof limits](#proof-limits)). No credential, token, or auth file was read or printed, and no model
or LLM call was made. `<root>` is the OpenCode config root and `<home>` the user's home directory.
Raw outputs and scripts stay outside the repository.

The Module versions and digests are those of the release record. The `plugins/`, `opencode/`, and
`codex/` trees and both marketplaces are byte-identical between `e6aceae`, where the Claude Code
marketplace clones stand, and `repo_head`.

### Why the OpenCode 1 plugin SDK could go

- Nothing used it. Neither `opencode.jsonc` has a `plugin` or `plugins` key, and neither config root
  has a `plugin/` or `plugins/` folder. Outside `node_modules`, the only script files are in deniz
  skill folders, and none imports a package from that `node_modules`. The only files that named
  `@opencode-ai/plugin` were `package.json` and its lock. The curator's switchboard install records
  list only Markdown agents, commands, and one skill, and the unowned skills hold no scripts. On the
  Linux host no OpenCode process mapped or held open a file under `node_modules`; on the Windows
  workstation the service process had loaded no module from it.
- OpenCode 2.0.26 neither needs nor writes it. In the 2.0.26 source, plugin sources come from the
  `plugins` config key and `plugin/` or `plugins/` folders
  (`packages/core/src/config/plugin/source.ts`, `packages/core/src/plugin/source-directory.ts`), npm
  plugin packages install into a `npm/` folder of the global cache (`packages/util/src/npm.ts`), and
  the plugin runtime provides only the host's `effect` and `@opencode/plugin` modules
  (`packages/plugin/src/runtime-modules.ts`, `runtime.ts`). No non-test source in the `core`,
  `plugin`, `cli`, `server`, or `util` packages names `@opencode-ai/plugin`, and none writes a
  `package.json` or `.gitignore` into a config folder; `missingPackageTarget` only computes a path to
  watch.
- Behavior agreed. The files had not changed since 2026-05-18 (Windows workstation) and 2026-07-06
  (Linux host), while OpenCode 2 ran from 2026-10-09. After the deletion, discovery was identical
  and no `package.json`, `package-lock.json`, `bun.lock`, or `node_modules` reappeared.

## Proof limits

- No before-inventory of Claude Code was kept in the WSL distro or on the Linux host; their before
  state rests on the 2026-10-09 record and the earlier version folders still in their caches.
- The Windows Codex before listing may show the versions of the marketplace clone that the desktop
  app had already upgraded, not the cache contents.
- Only the Windows Plan and Apply output was kept outside the repository; the per-Module counts come
  from it, and the other three Plans were compared with it during the rollout.
- The follow-up's discovery runs on the Windows workstation and the Linux host used the real OpenCode
  database: each run added one row for its throwaway folder to the database's `project` table (4 on
  the Windows workstation, 5 on the Linux host), with no session or message. Those rows were not
  removed. The WSL and macOS runs used a throwaway database.
- Discovery shows what the server lists. The model-facing skill guidance was not hashed, and agent
  permissions were not compared.
- The new Codex installs were checked by listing, cache bytes, and configuration only; no Codex
  session loaded them.
- The surviving services are one sample each: one Windows Apply that changed files, and one Linux
  update Apply against a running service. They do not refute `anomalyco/opencode#47505`.
