# installer-v0.6.0 estate rollout

This record covers the curator-approved rollout that followed the
[`installer-v0.6.0` Release](2026-10-12-opencode-installer-v0.6.0.md). It repeats the method of the
[v0.5.0 rollout](2026-10-11-v0.5.0-rollout.md). The real-profile updates are authorized changes, not
isolated panels. `isolation_ok: false` because every step ran against the real profiles; the
discovery servers redirected only the database and the project folder (see
[proof limits](#proof-limits)). No credential, token, or auth file was read or printed, and no model
or LLM call was made. `<root>` is the OpenCode config root and `<home>` the user's home directory.
Raw outputs and scripts stay outside the repository.

The Module versions and digests are those of the release record. The `plugins/`, `opencode/`, and
`codex/` trees and both marketplaces are byte-identical between `04b3969`, where every Claude Code
and Codex marketplace clone stands after the update, and `repo_head`.

## Claude Code and Codex plugin updates

Before the update, every `deniz-skills` row and cache in every environment was at the
[v0.5.0 rollout](2026-10-11-v0.5.0-rollout.md) versions: Process 0.8.0, General 0.12.0, Akka 0.4.1,
and Aspire 0.5.1. This time the before state was listed in all three environments. Only
`deniz-skills` rows were updated.

## OpenCode update with the installer-v0.6.0 Package

Each environment followed the README recipe: it downloaded the public asset, checked its SHA-256
against `package_sha256`, and ran `deniz-skills status`, then `update` (Plan), `update --yes`
(Apply), and `status` again. The Windows workstation downloaded the asset with `gh release
download`; the other three downloaded the public URL without authentication. No environment sets
`OPENCODE_CONFIG_DIR` or `XDG_CONFIG_HOME`, so each Destination is `<home>/.config/opencode`.

- Before: `status` listed Akka `current` and the other three Modules `differs`, with Lock none and
  Recovery none.
- Plan: identical in all four environments, compared by a digest of the Plan text without its
  Destination line. `Selection: unchanged` for each Module; Akka `No changes.`; Aspire 2 replaces;
  General 1 add and 21 replaces; Process 7 replaces. In total 1 add, 30 replaces, and no removes,
  with no Collisions or findings. The add is `sdk-container-publishing`'s real-world examples. These
  operations equal the `opencode/` diff between the two release sources: 1 added and 30 changed
  Native files plus three changed Bundle manifests. The Apply printed the same Plan.
- After Apply, `status` listed the four Modules current with Lock none and Recovery none. A re-read
  of each Install state found schema 2, the four release digests, and 327 file records whose
  SHA-256 values all match the files on disk; 112 dotted skill folders and 2 dotted agents.
- Services: on the Windows workstation the managed service process that started on 2026-10-10 was
  still running after the Apply and after the discovery runs, and the Apply printed the installer's
  `anomalyco/opencode#47505` warning, as designed for a Windows Apply that changed files. The Linux
  host's systemd user service kept its 2026-10-09 start time and main process, with 0 restarts. In
  the WSL distro no OpenCode process ran before or after, and its service stayed stopped. The macOS
  workstation has no service.

### Discovery

A short-lived private `opencode serve` on loopback with a random password, an empty throwaway
project folder, and a throwaway `OPENCODE_DB` read `GET /api/skill` until four consecutive reads
agreed, then `GET /api/agent`; its process tree was then killed and the throwaway folder deleted.
Every run confirmed that the server had stopped, and every run except the first Windows one, which
did not yet check it, confirmed that the throwaway database had been created. The deniz rows (ID,
hidden flag, and SHA-256 of the returned content) are identical in all four environments. The 112
deniz IDs equal the Bundles' skill folders, and the 30 hidden IDs equal the repository's `manual`
set. The check ran four times on the Windows workstation and twice in the WSL distro while the
script's output was refined; the deniz rows were the same in every run that printed them.

| Environment | Skills | Deniz skills | Other skills | Agents |
|---|---|---|---|---|
| Windows workstation | 127 | 112 (82 advertised, 30 hidden) | 2 built-in, 3 unowned in `<root>/skills`, 10 through the Claude compatibility path | 45 (5 primary, 40 subagent), both deniz agents as subagents |
| WSL distro | 127 | 112 (82, 30) | 2 built-in, 13 through the Claude compatibility path | 9 (5 primary, 4 subagent), both deniz agents as subagents |
| Linux host | 114 | 112 (82, 30) | 2 built-in | 9 (5 primary, 4 subagent), both deniz agents as subagents |
| macOS workstation | 114 | 112 (82, 30) | 2 built-in | 9 (5 primary, 4 subagent), both deniz agents as subagents |

The WSL distro's Claude compatibility path held 2 skills in the
[v0.5.0 rollout](2026-10-11-v0.5.0-rollout.md#discovery-after-the-follow-up) and holds 13 now. Those
skills are not installer-owned, and this rollout did not change or investigate them.

## Proof limits

- The discovery servers read the real config root, which is their purpose, and used the real data,
  cache, and state roots; only the database and the project folder were throwaway. On the Linux host
  the real database's modification time predates the run, while the shared OpenCode log file and
  the `shell` folder under the data root changed during the run window, by the private server or by
  the running service.
- Discovery shows what the server lists. The model-facing skill guidance was not hashed, and agent
  permissions were not compared. The Windows agent count is reported by mode only.
- Cache comparisons use Git blob hashes, so they are independent of checkout line endings; Windows
  does not record POSIX modes, so executable bits were checked only in the WSL distro and on the
  Linux host.
- The Codex updates were checked by listing, cache bytes, and configuration only; no Codex session
  loaded them.
- The surviving services are one more sample each: one Windows Apply that changed 31 files and one
  Linux update Apply against a running service. They do not refute `anomalyco/opencode#47505`.
