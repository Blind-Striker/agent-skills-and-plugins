# installer-v0.7.1 estate rollout

This record covers the curator-approved rollout that followed the
[`installer-v0.7.1` Release](2026-10-12-opencode-installer-v0.7.1.md). It repeats the method of the
[v0.7.0 rollout](2026-10-12-v0.7.0-rollout.md), except that every discovery check used the
[runbook](../runbook.md)'s real-profile method. The real-profile updates are authorized changes,
not isolated panels. `isolation_ok: false` because every step ran against the real profiles. No
credential, token, or auth file was read or printed, and no model or LLM call was made. `<root>` is
the OpenCode config root and `<home>` the user's home directory. Raw outputs and scripts stay
outside the repository.

The Module versions and digests are those of the release record. The `plugins/`, `opencode/`, and
`codex/` trees and both marketplaces are byte-identical between `bdee06a`, where every Claude Code
and Codex marketplace clone stands after the update, and `repo_head`.

Each `harness_version` was read from install metadata only: the `package.json` of the installed npm
package, or the version folder that the native Claude Code launcher resolves to. No harness binary
ran to print its version. Claude Code on the Linux host reads 2.1.296, where the
[v0.7.0 rollout](2026-10-12-v0.7.0-rollout.md) read 2.1.286; this rollout did not update it.

## Claude Code and Codex plugin updates

Before the update, every `deniz-skills` row and cache in every environment was at the
[v0.7.0 rollout](2026-10-12-v0.7.0-rollout.md) versions: Process 0.10.0, General 0.14.0, Akka 0.4.1,
and Aspire 0.6.0. The before state was read from the plugin files, without starting a harness. Only
`deniz-skills` rows were updated.

## OpenCode update with the installer-v0.7.1 Package

Each environment followed the README recipe: it obtained the public asset, checked its SHA-256
against `package_sha256`, and ran `deniz-skills status`, then `update` (Plan), `update --yes`
(Apply), and `status` again. The Windows workstation used its unauthenticated public re-download
from the release check; the other three downloaded the public URL without authentication. No
environment sets `OPENCODE_CONFIG_DIR` or `XDG_CONFIG_HOME`, so each Destination is
`<home>/.config/opencode`. All four Plans were read before the first Apply.

- Before: `status` listed Akka, Aspire, and General `current` and Process `differs`, with Lock none
  and Recovery none.
- Plan: identical in all four environments, compared by a digest of the Plan text without its
  Destination line. `Selection: unchanged` for each Module; Akka, Aspire, and General
  `No changes.`; Process 2 replaces, the `SKILL.md` and `references/harness-tools.md` of
  `verified-waves`. No adds, removes, Collisions, or findings. These operations equal the `opencode/`
  diff between the two release sources: 2 changed Native files plus Process's Bundle manifest. Each
  Apply printed the same Plan; the Windows one added the warning below.
- After Apply, `status` listed the four Modules current with Lock none and Recovery none. A re-read
  of each Install state found schema 2, the four release digests, and 329 file records whose
  SHA-256 values all match the files on disk; 113 dotted skill folders and 2 dotted agents.
- Services: on the Windows workstation the managed service process that started on 2026-10-10 was
  still running after the Apply and after the discovery run, and the Apply printed the installer's
  `anomalyco/opencode#47505` warning, as designed for a Windows Apply that changed files. The Linux
  host's systemd user service kept its 2026-10-09 start time and main process, with 0 restarts. In
  the WSL distro no OpenCode process ran before or after, and its service stayed stopped. The macOS
  workstation has no service.

### Discovery

Each environment ran the runbook's real-profile method once, after its Apply: a short-lived private
`opencode serve` on loopback with a random password and an empty throwaway project folder, with
`HOME` and the config root real, and `XDG_DATA_HOME`, `XDG_STATE_HOME`, `XDG_CACHE_HOME`, and
`OPENCODE_DB` in one throwaway folder. It read `GET /api/skill` until four consecutive reads agreed,
then `GET /api/agent`; its process tree was then killed and the throwaway folder deleted. Every run
confirmed that the server had stopped, that it had created its database, log, state, and cache below
the throwaway folder, and that the folder was gone afterwards. The deniz rows (ID, hidden flag, and
SHA-256 of the returned content) are identical in all four environments. The 113 deniz IDs equal the
Bundles' skill folders, and the 31 hidden IDs equal the repository's `manual` set;
`deniz-process.verified-waves` is among them, listed hidden in all four environments.

| Environment | Skills | Deniz skills | Other skills | Agents |
|---|---|---|---|---|
| Windows workstation | 128 | 113 (82 advertised, 31 hidden) | 2 built-in, 3 unowned in `<root>/skills`, 10 through the Claude compatibility path | 45 (5 primary, 40 subagent), both deniz agents as subagents |
| WSL distro | 128 | 113 (82, 31) | 2 built-in, 13 through the Claude compatibility path | 9 (5 primary, 4 subagent), both deniz agents as subagents |
| Linux host | 115 | 113 (82, 31) | 2 built-in | 9 (5 primary, 4 subagent), both deniz agents as subagents |
| macOS workstation | 115 | 113 (82, 31) | 2 built-in | 9 (5 primary, 4 subagent), both deniz agents as subagents |

The counts equal the [v0.7.0 rollout](2026-10-12-v0.7.0-rollout.md#discovery); only the content of
`verified-waves` changed the deniz rows' digest. One extra run on the Windows workstation, before
its Apply, listed the 0.7.0 rows with the digest that the v0.7.0 rollout recorded, so the new method
lists the same rows as the old one.

Around every discovery run, the modification times of the real log, the real database, the newest
entry below the real state root, and the newest entry below the real cache root were read before and
after; none changed in any environment. The macOS workstation has no database at that path. In the
WSL distro no other OpenCode process ran, so that run is a quiet control. On the Windows workstation
and the Linux host the running service wrote nothing to the log during the run. On the macOS
workstation, other short-lived OpenCode CLI processes, not started by this rollout, wrote to the log
a few minutes before the run, and none during it.

## Proof limits

- The discovery servers read the real config root and the Claude compatibility paths below the
  home, which is their purpose. The system temp folder's `opencode` directory was not moved and was
  not measured.
- "Unchanged" for the real roots means unchanged modification times over one short run in each
  environment. A running service could have written during a longer run; these are samples.
- Discovery shows what the server lists. The model-facing skill guidance was not hashed, and agent
  permissions were not compared. The Windows agent count is reported by mode only.
- Cache comparisons use Git blob hashes, so they are independent of checkout line endings; Windows
  does not record POSIX modes, so executable bits were checked only in the WSL distro and on the
  Linux host.
- The Codex updates were checked by listing, cache bytes, and configuration only; no Codex session
  loaded them.
- The surviving services are one more sample each: one Windows Apply that changed 2 files and one
  Linux update Apply against a running service. They do not refute `anomalyco/opencode#47505`.
