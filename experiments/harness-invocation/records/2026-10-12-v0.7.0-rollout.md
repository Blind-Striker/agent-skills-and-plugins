# installer-v0.7.0 estate rollout

This record covers the curator-approved rollout that followed the
[`installer-v0.7.0` Release](2026-10-12-opencode-installer-v0.7.0.md). It repeats the method of the
[v0.6.0 rollout](2026-10-12-v0.6.0-rollout.md). The real-profile updates are authorized changes, not
isolated panels. `isolation_ok: false` because every step ran against the real profiles; the
discovery servers redirected only the database and the project folder (see
[proof limits](#proof-limits)). No credential, token, or auth file was read or printed, and no model
or LLM call was made. `<root>` is the OpenCode config root and `<home>` the user's home directory.
Raw outputs and scripts stay outside the repository.

The Module versions and digests are those of the release record. The `plugins/`, `opencode/`, and
`codex/` trees and both marketplaces are byte-identical between `32b06a8`, where every Claude Code
and Codex marketplace clone stands after the update, and `repo_head`.

Each `harness_version` was read from install metadata only: the `package.json` of the installed npm
package, or the version folder that the native Claude Code launcher resolves to. No harness binary
ran to print its version.

## Claude Code and Codex plugin updates

Before the update, every `deniz-skills` row and cache in every environment was at the
[v0.6.0 rollout](2026-10-12-v0.6.0-rollout.md) versions: Process 0.8.1, General 0.13.0, Akka 0.4.1,
and Aspire 0.6.0. The before state was read from the plugin files, without starting a harness. Only
`deniz-skills` rows were updated.

  Akka 17, Aspire 49 files; `.in_use/<pid>` session markers excluded); in the WSL distro and on the

  the Windows default profile's `settings.json`; it was compared again after the WSL update and is

- Running Claude Code and Codex sessions keep the plugin versions they loaded until they restart.
  No session was started or restarted.

## OpenCode update with the installer-v0.7.0 Package

Each environment followed the README recipe: it downloaded the public asset, checked its SHA-256
against `package_sha256`, and ran `deniz-skills status`, then `update` (Plan), `update --yes`
(Apply), and `status` again. The Windows workstation downloaded the asset with `gh release
download`; the other three downloaded the public URL without authentication. No environment sets
`OPENCODE_CONFIG_DIR` or `XDG_CONFIG_HOME`, so each Destination is `<home>/.config/opencode`. All
four Plans were read before the first Apply.

- Before: `status` listed Akka and Aspire `current` and General and Process `differs`, with Lock
  none and Recovery none.
- Plan: identical in all four environments, compared by a digest of the Plan text without its
  Destination line. `Selection: unchanged` for each Module; Akka and Aspire `No changes.`; General 1
  replace; Process 2 adds and 1 replace. In total 2 adds, 2 replaces, and no removes, with no
  Collisions or findings. The adds are `verified-waves`'s `SKILL.md` and
  `references/harness-tools.md`; the replaces are the `SKILL.md` of Process's `ask-deniz` and of
  General's `writing-tunit-tests`. These operations equal the `opencode/` diff between the two
  release sources: 2 added and 2 changed Native files plus two changed Bundle manifests. Each Apply
  printed the same Plan; the Windows one added the warning below.
- After Apply, `status` listed the four Modules current with Lock none and Recovery none. A re-read
  of each Install state found schema 2, the four release digests, and 329 file records whose
  SHA-256 values all match the files on disk; 113 dotted skill folders and 2 dotted agents.
- Services: on the Windows workstation the managed service process that started on 2026-10-10 was
  still running after the Apply and after the discovery run, and the Apply printed the installer's
  `anomalyco/opencode#47505` warning, as designed for a Windows Apply that changed files. The Linux
  host's systemd user service kept its 2026-10-09 start time and main process, with 0 restarts. In
  the WSL distro no OpenCode process ran before or after, and its service stayed stopped. The macOS
  workstation has no service.

### Discovery

A short-lived private `opencode serve` on loopback with a random password, an empty throwaway
project folder, and a throwaway `OPENCODE_DB` read `GET /api/skill` until four consecutive reads
agreed, then `GET /api/agent`; its process tree was then killed and the throwaway folder deleted.
It ran once in each environment. Every run confirmed that the server had stopped and that the
throwaway database had been created. The deniz rows (ID, hidden flag, and SHA-256 of the returned
content) are identical in all four environments. The 113 deniz IDs equal the Bundles' skill
folders, and the 31 hidden IDs equal the repository's `manual` set; `deniz-process.verified-waves`
is among them, listed hidden in all four environments.

|---|---|---|---|---|
| Windows workstation | 128 | 113 (82 advertised, 31 hidden) | 2 built-in, 3 unowned in `<root>/skills`, 10 through the Claude compatibility path | 45 (5 primary, 40 subagent), both deniz agents as subagents |
| WSL distro | 128 | 113 (82, 31) | 2 built-in, 13 through the Claude compatibility path | 9 (5 primary, 4 subagent), both deniz agents as subagents |
| Linux host | 115 | 113 (82, 31) | 2 built-in | 9 (5 primary, 4 subagent), both deniz agents as subagents |

Each skill count is one more than in the [v0.6.0 rollout](2026-10-12-v0.6.0-rollout.md#discovery),
and the other skills and the agents are unchanged.

## Proof limits

- The discovery servers read the real config root, which is their purpose, and used the real data,
  cache, and state roots; only the database and the project folder were throwaway. In every
  environment the real OpenCode log file grew during the discovery run, while the real database's
  modification time did not change; the macOS workstation has no database at that path. In the WSL
  distro and on the macOS workstation no other OpenCode process ran, so the private server wrote
  those log lines.
- Discovery shows what the server lists. The model-facing skill guidance was not hashed, and agent
  permissions were not compared. The Windows agent count is reported by mode only.
- Cache comparisons use Git blob hashes, so they are independent of checkout line endings; Windows
  does not record POSIX modes, so executable bits were checked only in the WSL distro and on the
  Linux host.
- The Codex updates were checked by listing, cache bytes, and configuration only; no Codex session
  loaded them.
- The surviving services are one more sample each: one Windows Apply that changed 4 files and one
  Linux update Apply against a running service. They do not refute `anomalyco/opencode#47505`.
